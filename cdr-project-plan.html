Vision Recap
Rappel de la vision

CDR v2 — Hybrid Edge + Sovereign Cloud + Federated Analytics

CDR v2 — Périphérie hybride + nuage souverain + analytique fédérée

A coast-to-coast network of locally-owned AI compute nodes where Canadian institutions share knowledge without sharing data. Each station runs AI locally on protected data that never leaves. When someone builds something brilliant, it gets published to the Protocol Registry — a shared library that any other station can discover, adapt, and improve.

Un réseau pancanadien de nœuds de calcul IA détenus localement où les institutions canadiennes partagent le savoir sans partager les données. Chaque station exécute l'IA localement sur des données protégées qui ne quittent jamais les lieux. Quand quelqu'un crée quelque chose de brillant, c'est publié au Registre de protocoles — une bibliothèque partagée que toute autre station peut découvrir, adapter et améliorer.

🖥️ Hybrid Edge

Hardware-agnostic CDR-OS runs on Apple Silicon, NVIDIA, or AMD. Institutions own their stations. Data never leaves.

☁️ Sovereign Cloud Backbone

ThinkOn + Hypertec + Aptum consortium for overflow, federated queries, and Protected B cloud processing. 100% Canadian jurisdiction.

📊 Federated Analytics

Query goes to data, aggregated results come back. Differential privacy, containerized queries, compatible with Tableau/Power BI.

🖥️ Périphérie hybride

CDR-OS agnostique du matériel fonctionne sur Apple Silicon, NVIDIA ou AMD. Les institutions possèdent leurs stations. Les données restent sur place.

☁️ Dorsale de nuage souverain

Consortium ThinkOn + Hypertec + Aptum pour le débordement, les requêtes fédérées et le traitement nuage Protégé B. Juridiction 100% canadienne.

📊 Analytique fédérée

La requête va aux données, les résultats agrégés reviennent. Confidentialité différentielle, requêtes conteneurisées, compatible Tableau/Power BI.

Internal Extraction — Wilma → Node 2

Extraction interne — Wilma → Nœud 2

Prove that a protocol built at one station can be extracted, deployed on a fresh instance, and work without any of the original data. Wilma (Station Zero) is the first test subject.

Prouver qu'un protocole construit à une station peut être extrait, déployé sur une instance neuve et fonctionner sans aucune des données originales. Wilma (Station Zéro) est le premier sujet de test.

What Gets Extracted

  • AI assistant architecture (multi-agent, memory, context management)
  • Workflow patterns, pipeline definitions, agent configs
  • Tool integrations (abstracted — no credentials, no endpoints)
  • Prompt engineering patterns, reverse prompting methodology
  • File structure conventions, skill definitions

How It's Verified

✓ Success Criteria

  • VAP linter passes — zero protected references detected
  • Node 2 boots with Terry, guides new user through setup
  • New user productive within 2 hours (builds first tool)
  • grep -ri private terms returns zero results

✗ Failure Conditions

  • grep finds ANY private data in the extracted protocol
  • Node 2 requires manual configuration beyond user identity
  • Terry fails to guide onboarding without human intervention

Ce qui est extrait

  • Architecture de l'assistant IA (multi-agent, mémoire, gestion du contexte)
  • Modèles de flux de travail, définitions de pipelines, configs d'agents
  • Intégrations d'outils (abstraites — pas d'identifiants, pas de points de terminaison)
  • Modèles d'ingénierie de prompts, méthodologie de prompts inversés
  • Conventions de structure de fichiers, définitions de compétences

Comment c'est vérifié

✓ Critères de succès

  • Le linter VAP passe — zéro références protégées détectées
  • Le nœud 2 démarre avec Terry, guide le nouvel utilisateur
  • Nouvel utilisateur productif en moins de 2 heures
  • grep -ri termes privés retourne zéro résultat

✗ Conditions d'échec

  • grep trouve N'IMPORTE QUELLE donnée privée dans le protocole
  • Le nœud 2 nécessite une configuration manuelle au-delà de l'identité
  • Terry échoue à guider l'intégration sans intervention humaine

Government Validation — TBS Protected B Assessment

Validation gouvernementale — Évaluation Protégé B du SCT

Runs in parallel with Stages A–C. Goal: obtain the certifications needed to process Government of Canada Protected B data on CDR infrastructure.

Se déroule en parallèle avec les étapes A–C. Objectif : obtenir les certifications nécessaires pour traiter les données Protégé B du gouvernement du Canada sur l'infrastructure CDR.

What CDR Must Pass

  • Security Assessment & Authorization (SA&A)
  • ITSG-33 security control profile compliance
  • Data residency verification (Canadian soil only)
  • Encryption-in-transit and at-rest audit
  • Access control and audit logging review
  • Vulnerability assessment and penetration testing

Strategic Advantage

ThinkOn partnership accelerates this. The ThinkOn consortium already holds Protected B certification for their sovereign cloud services. CDR's cloud backbone inherits this trust chain.

Edge stations add a new assessment surface — but simpler: no remote access, no network exposure, institution-controlled. The attack surface is minimal by design.

Timeline

Months 1–2: Documentation, threat model, control mapping
Months 3–4: Assessment engagement with TBS-accredited assessor
Months 5–6: Remediation, final assessment, interim Authority to Operate

Ce que le CDR doit réussir

  • Évaluation et autorisation de sécurité (EA&A)
  • Conformité au profil de contrôles de sécurité ITSG-33
  • Vérification de la résidence des données (sol canadien uniquement)
  • Audit du chiffrement en transit et au repos
  • Examen du contrôle d'accès et de la journalisation
  • Évaluation des vulnérabilités et tests d'intrusion

Avantage stratégique

Le partenariat ThinkOn accélère cela. Le consortium ThinkOn détient déjà la certification Protégé B. La dorsale nuage du CDR hérite de cette chaîne de confiance.

Les stations de périphérie ajoutent une nouvelle surface d'évaluation — mais plus simple : pas d'accès distant, pas d'exposition réseau, contrôle institutionnel.

Chronologie

Mois 1–2 : Documentation, modèle de menaces, cartographie des contrôles
Mois 3–4 : Engagement d'évaluation avec évaluateur accrédité SCT
Mois 5–6 : Remédiation, évaluation finale, autorité d'exploitation intérimaire

Risk Register
Registre des risques

Top Risks and Mitigations

Principaux risques et atténuations

🍎 Apple Hardware Dependency
Over-reliance on a single US-based hardware vendor for edge stations
✓ Mitigated: CDR-OS is hardware-agnostic. Hypertec CIARA (Canadian) is the flagship. MLX/CUDA/ROCm abstraction layer.
🤖 Terry Quality at Scale
AI assistant may not handle diverse institution types or complex workflows reliably
✓ Mitigated: Built on Clawdbot, battle-tested across thousands of hours. Phase 0 validates with 3 diverse sectors before scaling.
🔓 Protocol Data Leakage
Protected information could inadvertently leak through published protocols
✓ Mitigated: VAP is constructive (born clean), not subtractive. Linter + human review. grep test as acid test. Metadata taxonomy defined.
🏛️ Government Sales Cycle
Federal procurement and certification timelines can stretch 12–24+ months
✓ Mitigated: ThinkOn partnership provides existing GC relationships. Small business + university pilots generate revenue while GC pipeline develops.
📉 Network Effects Stall
Not enough stations join to create the knowledge-sharing flywheel
✓ Mitigated: Each station has standalone value (local AI). Network effects are bonus. Phase 0 proves value at 4 stations before scaling.
🔧 Open-Source Sustainability
Open core model must fund development while keeping trust through transparency
✓ Mitigated: Red Hat model proven at scale. Managed service + premium registry + enterprise contracts provide revenue. Core stays open.
🍎 Dépendance au matériel Apple
Dépendance excessive envers un seul fournisseur de matériel basé aux É.-U.
✓ Atténué : CDR-OS est agnostique du matériel. Hypertec CIARA (canadien) est le produit phare. Couche d'abstraction MLX/CUDA/ROCm.
🤖 Qualité de Terry à l'échelle
L'assistant IA pourrait ne pas gérer de manière fiable des types d'institutions diversifiés
✓ Atténué : Construit sur Clawdbot, éprouvé sur des milliers d'heures. Phase 0 valide avec 3 secteurs avant la mise à l'échelle.
🔓 Fuite de données via protocoles
Des informations protégées pourraient fuir à travers les protocoles publiés
✓ Atténué : VAP est constructif (né propre), pas soustractif. Linter + revue humaine. Test grep comme test décisif.
🏛️ Cycle de vente gouvernemental
Les délais d'approvisionnement et de certification fédéraux peuvent s'étirer sur 12–24+ mois
✓ Atténué : Le partenariat ThinkOn fournit des relations GC existantes. Les pilotes PME + universités génèrent des revenus en attendant.
📉 Stagnation des effets de réseau
Pas assez de stations rejoignent pour créer l'effet d'entraînement du partage de connaissances
✓ Atténué : Chaque station a une valeur autonome (IA locale). Phase 0 prouve la valeur à 4 stations avant de grandir.
🔧 Durabilité du code ouvert
Le modèle noyau ouvert doit financer le développement tout en maintenant la confiance
✓ Atténué : Modèle Red Hat prouvé à l'échelle. Service géré + registre premium + contrats entreprise fournissent les revenus.
